# ネットワークモニターサーバ 方式設計

## 1. 文書情報
- 文書名: ネットワークモニターサーバ 方式設計
- 作成日: 2026-03-16
- 対象プロジェクト: `net-monitor-mini`
- 参照元: `.docs/requirements.md`

## 2. 設計目的
- 要件定義を満たすためのシステム全体方針を定める
- 今後の機能追加に耐える構成を先に決め、後続実装の手戻りを減らす
- 初期リリースで必要十分なシンプルさと、拡張性の両立を図る

## 3. 採用方針

### 3.1 基本方針
- 初期リリースは `Windows 上で常駐する Python バックエンド` と `ローカル Web UI` の構成を採用する
- 監視処理、保存処理、表示処理を明確に分離する
- 監視対象追加や監視方式追加を見据え、内部はプラグイン追加しやすい責務分割とする

### 3.2 採用理由
- AGENTS.md の方針上、Web アプリケーションやバッチ系は Python を優先採用するのが適合する
- 初期機能は ping 実行、定期実行、データ保存、グラフ表示であり、Web UI で十分に要件を満たせる
- Electron を初期採用すると、UI 実装コストと配布構成が相対的に重くなる
- Python は常駐処理、スケジューリング、SQLite、ローカル API 実装の組み合わせに適している
- 将来的に UI を強化する場合も、バックエンドを維持したままフロントエンドだけ段階的に差し替えやすい

## 4. システム構成方針

### 4.1 論理構成
- `app`: アプリケーション起動制御
- `scheduler`: 定期実行管理
- `monitoring`: 監視処理本体
- `storage`: 監視結果保存
- `api`: UI 向けデータ提供
- `ui`: ローカルブラウザで開く監視画面
- `config`: 設定読込・検証
- `logging`: ログ出力

### 4.2 実行形態
- 1 つの Python プロセスでバックエンド機能を提供する
- バックエンドは起動時に以下を順番に初期化する
  - 設定読込
  - ストレージ初期化
  - スケジューラ起動
  - Web API 起動
- UI はローカルホストで公開された Web 画面をブラウザで参照する

### 4.3 常駐方式
- 初期リリースは `通常アプリケーションとして常駐` を採用する
- Windows サービス化は将来拡張とし、内部構成はサービス化しやすいように UI 依存を分離する

## 5. 処理方式

### 5.1 監視実行方式
- 監視対象ごとに 5 分間隔で監視ジョブを起動する
- 1 監視ジョブ内で ping を 3 回実行する
- 3 回の結果は個別記録しつつ、1 監視サイクルとして集約可能にする
- 1 対象の失敗は他対象のスケジュールに影響させない

### 5.2 スケジューリング方式
- アプリ内部スケジューラでジョブ管理する
- OS タスクスケジューラには依存しない
- 定期実行時刻はアプリ起動基準ではなく、一定間隔で安定実行できる方式を採用する

### 5.3 保存方式
- 初期リリースはローカル永続化を採用する
- 保存先はローカル DB を基本とする
- 結果データと設定データを論理的に分離する

### 5.4 表示方式
- UI はローカル Web 画面とする
- UI は保存済みデータを API 経由で取得してグラフ描画する
- 監視処理の状態と可視化処理を疎結合にする

## 6. 主要ユースケース

### 6.1 監視開始
1. 利用者がアプリを起動する
2. アプリが設定と保存先を初期化する
3. スケジューラが有効な監視対象を登録する
4. 定期的に ping 監視を実行する

### 6.2 グラフ確認
1. 利用者がローカル UI を開く
2. UI が監視対象一覧を取得する
3. 利用者が対象を選択する
4. UI が時系列データを取得する
5. 応答時間推移と成功/失敗をグラフ表示する

### 6.3 監視失敗時
1. ping 実行がタイムアウトまたは名前解決失敗になる
2. 失敗結果を保存する
3. 後続ジョブは継続する
4. UI 上で失敗が識別できる

## 7. 拡張性方針

### 7.1 監視方式追加
- `monitoring` 配下に監視種別ごとの実装を追加できる構造とする
- 共通の実行結果モデルを持たせ、ping 以外の監視方式でも保存・表示へ接続しやすくする

### 7.2 通知機能追加
- 閾値判定や状態変化判定を独立レイヤとして追加できるようにする
- 通知先はメールやチャットなどを後付けできる設計とする

### 7.3 UI 強化
- UI と API を分離し、将来の画面再設計や SPA 化にも対応しやすくする

## 8. 障害時方針
- 単発の ping 失敗ではアプリ全体を停止しない
- 監視処理例外はジョブ単位で捕捉し、ログに記録する
- ストレージ障害時は API 側にも異常を伝達できるようにする
- 致命的な初期化失敗時のみ起動を中断する

## 9. セキュリティ方針
- 初期リリースはローカル利用を前提とし、API バインド先は `127.0.0.1` を基本とする
- 不要な外部公開は行わない
- 設定ファイル内の入力値は検証する

## 10. 運用方針
- 小規模環境での常駐監視を主用途とする
- 再起動後も保存済み履歴を参照できることを前提とする
- 将来的に自動起動設定を追加できるように、バックエンドは非対話起動にも対応しやすくする

## 11. 方式上の決定事項
- 言語の主軸は Python とする
- UI はローカル Web UI とする
- 保存はローカル DB 方式を採用する
- 初期版は単一マシン構成とする
- 初期版は通常アプリ常駐とし、Windows サービス化は保留とする

## 12. 今後の検討課題
- UI 自動起動の有無
- バックグラウンド起動時のトレイ常駐要否
- Windows サービス化の必要性
- 長期保存データのローテーション方針
